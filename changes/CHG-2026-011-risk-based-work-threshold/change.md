# 基于持久决策与风险的 Work 阈值

## 问题或目标

上一版文档比例规则把直接修改限制为少数示例，并错误地把新增测试视为必须建立 Work 的条件，仍会让普通局部 Bug、内部重构、类型修正、测试补强、开发工具和无语义性能改进产生多余文档。本变更用是否存在需要长期保存的决策或风险代替修改类型白名单。

## 预期行为

- Work 的判断依据是是否需要长期保存产品决策、契约、风险、迁移或跨任务协调，而不是 UI/Bug/重构等类别或 diff 大小。
- 修改若处于已接受行为内、影响局部且可逆、没有跨越高风险或公共契约边界，并能在当前任务完成验证，可以直接实施。
- 直接修改可以新增回归测试、调整局部测试基线或补强验证；测试变化本身不自动要求 Work。
- 普通局部 Bug、内部重构、类型/空值修正、测试和开发工具、无语义性能优化等都可以按通用判据直接处理。
- 只有产生持久决策价值或超过当前任务可控范围时才建立 Work；需要 Work 但风险有限时正文可以精简。

## 非目标

- 不允许按代码行数或“看起来很小”绕过安全、数据、格式、公共接口、迁移与兼容治理。
- 不删除统一 Change 模板、状态机或已有历史记录。
- 不修改产品 Requirement 或运行时行为。

## 影响范围

替代 `CHG-2026-010-documentation-proportionality` 的过窄判定，更新 AI Constitution、文档治理、模板说明、README 与门禁。产品代码和发布 Gate 无变化。

## 实现约束

- 直接修改必须能在当前任务完成实现和验证；需要跨任务计划、产品选择、迁移、发布协调或长期风险记录时建立 Work。
- 安全/信任、secret、数据所有权、持久化/格式、公共 API/RPC/IPC/ABI、兼容、平台范围和不可逆操作始终需要 Work。
- 严重、反复出现、根因不明、涉及数据丢失或安全的 Bug 需要 Work；明确、局部、可回归验证的普通 Bug 可以直接修复。
- 示例只能帮助理解，不得反向解释为未列出的修改必须建 Work。
